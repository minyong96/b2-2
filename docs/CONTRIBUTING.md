# Contributing Guide

우리 팀의 협업 규칙입니다. 모든 작업은 이 문서를 기준으로 진행합니다.

## 브랜치 전략(GitHub Flow)
- `main`: 항상 깨지지 않는 상태를 유지한다. 직접 push 금지, PR로만 병합한다.
- `feature/*`: 작업 단위 브랜치. 작업이 끝나면 PR을 올리고, 병합 후 브랜치는 더 쓰지 않는다.

우리 팀이 GitHub Flow를 선택한 이유:
1. 규칙이 `main`과 `feature/*` 두 가지뿐이라 팀원 모두가 바로 따라 할 수 있다.
2. 모든 변경이 PR을 거치므로 코드 리뷰와 작업 기록이 자연스럽게 남는다.
3. `main`이 항상 안정적이어서 충돌과 실수가 생겨도 되돌리기 쉽다.

## 브랜치 네이밍 규칙
- 형식: `feature/<이름>-<작업내용>` (소문자, 단어는 `-`로 연결)
- 예: `feature/ungblack-string-utils`, `feature/milkyjung-math-utils`, `feature/leader-contributing`
- 한 브랜치에는 한 이슈의 작업만 담는다.

## 커밋 메시지 컨벤션
- 형식: `<type>: <무엇을 어떻게 바꿨는지>`

| type | 용도 |
|---|---|
| `feat` | 기능/함수 추가 |
| `fix` | 버그 수정 |
| `docs` | 문서 추가/수정 |
| `refactor` | 동작 변화 없는 코드 정리, 파일 이동 |
| `test` | 테스트 추가/수정 |
| `chore` | 설정, 폴더 구조 등 기타 |

- 좋은 예: `feat: 문자열 뒤집기 함수 reverse_string 추가`
- 금지 예 (변경 대상을 알 수 없는 메시지): `update`, `fix`, `temp`, `wip`, `final`
- 금지 예 (무엇을/왜 바꿨는지 없는 메시지): `bug fix`, `edit file`

## PR 규칙
- 모든 변경은 `feature/*` 브랜치에서 PR로 `main`에 병합한다.
- 제목은 커밋 컨벤션과 같은 형식으로 쓴다.
- 본문에 아래 항목을 반드시 넣는다. (`.github/PULL_REQUEST_TEMPLATE.md` 사용)
  - `Closes #이슈번호` (이슈 번호이며 PR 번호가 아니다)
  - 변경 사항(What)
  - 변경 이유(Why)
  - 테스트/검증 방법(How)
- 병합 조건: 리뷰어 1명 이상의 승인(Approve)이 있고, 실질 코멘트가 1개 이상 있어야 한다.
- 병합은 Merge commit 방식을 쓴다. (Squash/Rebase 사용 안 함)

## 코드 리뷰 규칙
- 모든 PR은 작성자 외 1명 이상이 리뷰한다.
- `LGTM`, `좋아요`만 남기는 리뷰는 금지한다. 특정 파일/라인을 근거로 아래 중 하나 이상을 남긴다.
  - 질문: "이 함수는 빈 입력일 때 어떻게 동작하나요?"
  - 대안 제안: "이 부분은 `text[::-1]` 대신 `reversed()`를 쓰면 의도가 더 분명할 것 같아요."
  - 리스크 지적: "음수를 넣으면 결과가 헷갈릴 수 있어 보여요."
  - 개선 제안: "docstring에 사용 예시를 한 줄 더 넣으면 좋겠어요."
- 작성자는 리뷰 코멘트에 답글을 달거나 수정 커밋으로 반영하고, 반영한 커밋 해시를 답글에 남긴다.
- 리뷰어와 작성자는 최소 1회 서로 주고받은 기록을 남긴다.

## 충돌 발생 시 대응 흐름
1. **발생**: `git merge main` 또는 PR의 "This branch has conflicts" 표시로 확인한다.
2. **공유**: 충돌이 난 사람이 팀 채널에 어느 브랜치/파일인지 알린다. 혼자 판단이 어려우면 마지막으로 해당 파일을 수정한 사람에게 묻는다.
3. **해결**: 충돌이 난 사람이 자기 브랜치에서 해결한다. 충돌 마커(`<<<<<<<`, `=======`, `>>>>>>>`)를 지우고 양쪽 의도를 확인해 합친다. `main`에서 해결하거나 강제 push(`--force`)하지 않는다.
4. **기록**: `docs/conflict-resolution.md`에 상황, 충돌 마커 원문, 해결 방법, 결과를 템플릿대로 남긴다.

## 공유 브랜치 안전 규칙
- `main` 등 공유 브랜치에서 히스토리 재작성(reset, rebase, 강제 push)을 하지 않는다.
- 이미 push한 커밋을 취소할 때는 `git revert`를 쓴다.
- 팀 합의 없이 강제 push/rebase를 하지 않는다.
